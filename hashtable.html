hashtable

A key gets hashed to a number, then dropped into bucket = hash % size. Two keys landing on the same bucket is a collision — this table resolves it by chaining, and resizes once it gets crowded.

how it works

Hashing turns an arbitrary key (here, a string) into a number, using a formula that mixes every character together — this page multiplies a running total by 31 and adds each character's code, a common simple approach. That raw number is then reduced with % size (size = number of buckets) so it always lands on a valid bucket index, no matter how large the original hash was.

Collisions happen when two different keys hash to the same bucket — with enough keys and a fixed number of buckets, this is mathematically unavoidable (the pigeonhole principle). This table handles it with chaining: each bucket holds a small list, and a colliding key just gets appended to that bucket's list instead of overwriting anything. Looking up a key means hashing it to find the right bucket, then scanning that bucket's short list.

Load factor (entries ÷ buckets) measures how crowded the table is getting. As it climbs, chains get longer and lookups get slower — approaching O(n) in the worst case instead of the O(1) average a hash table is supposed to give you. Once load factor crosses a threshold (0.75 here), the table resizes: it allocates more buckets and rehashes every existing key into the new, larger table, since hash % size gives a different answer once size changes.
